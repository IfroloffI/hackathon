# Спецификация: мультиплеерный каркас «Хронолёта»

> Что сделано, как устроено и почему так. Состояние на 2026-10-31.
> Обзорная схема — [ARCHITECTURE.md](ARCHITECTURE.md), игровой дизайн — [chronolet-design.md](chronolet-design.md).

## 1. Цель и рамки

**Задача этапа:** сайт, на котором можно создать комнату, другие игроки присоединяются к ней, движения всех персонажей синхронизируются через бэкенд и сохраняются в БД. Всё работает на **одном хосте** в локальной сети без интернета.

**Входит:**
- лобби: имя, создание комнаты, вход по коду / из списка / по ссылке;
- HTTP API на Fastify: auth (имя → JWT), RoomManager (POST/DELETE /room, роли мастер/гость), отладочные ручки;
- UDP-бродкаст публичных комнат в LAN (`node:dgram`) и hello-канал `WS /room/{id}/connect` (событие «Hello world!» раз в секунду);
- комната-экипаж на Colyseus: синхронизация движения, чат, переподключение;
- SQLite: игроки, сессии, позиции, журнал событий;
- 2.5D-сцена хаба на three.js с физикой платформера;
- кнопка «Скопировать приглашение» со ссылкой на LAN-IP хоста;
- заготовка под ИИ-агентов (без LLM).

**Не входит (следующие этапы):** головоломки, предметы, роли, эпохи, логин с паролем, ИИ-персонажи, ассеты.

## 2. Технологии и почему

| Слой | Выбор | Почему |
|---|---|---|
| Язык | TypeScript везде | Общие типы сообщений и состояния для клиента и сервера (как в дизайн-доке). |
| Реалтайм | **Colyseus 0.18** | Требование задачи. Даёт из коробки матчмейкинг, комнаты, дельта-синхронизацию состояния и переподключение — вместо ручного `ws` из дизайн-дока. |
| HTTP | **Fastify** (владеет единственным `node:http`) | Требование API-слоя: auth, RoomManager, UDP-beacon, hello-WS. Fastify владеет портом, Colyseus-транспорт прицеплен через `attachToServer` с фильтром апгрейдов; matchmake-контракт SDK воспроизведён в Fastify-роуте. Пакет `express` остался только как зависимость `@colyseus/ws-transport`. |
| БД | **`node:sqlite`** (встроен в Node 22) | Один файл, ноль настройки, **нет нативных сборок** (у `better-sqlite3` они ломаются офлайн и на разных версиях Node). |
| Клиент | three.js + Vite | По дизайн-доку. Vite — быстрый HMR в разработке и статическая сборка для prod. |
| Запуск TS | `tsx` | Сервер запускается из исходников без шага компиляции; `shared` подключается как TS напрямую. |
| Node | 22 (закреплён через Volta) | Colyseus 0.18 требует `node >= 22`; `node:sqlite` без флага — с 22.13. |
| Монорепо | npm workspaces | `shared` / `server` / `client`, общий `node_modules`, одна установка. |

## 3. Топология «один хост»

```
Хост (npm run build && npm start)  ── порт 2567, слушает 0.0.0.0
  ├─ GET /                → client/dist (собранный клиент, SPA-fallback)
  ├─ /auth/*              → login → JWT, logout (blacklist), me
  ├─ /room*               → RoomManager (создать/удалить/disconnect)
  ├─ GET /api/*           → REST (комнаты, сессии, адреса хоста)
  ├─ /matchmake/*         → матчмейкинг Colyseus (контракт @colyseus/sdk)
  ├─ WebSocket            → комнаты Colyseus (state) + /room/{id}/connect (hello)
  ├─ UDP :41234           → бродкаст публичных комнат в LAN
  ├─ data/chronolet.db    → SQLite
  └─ (позже) Ollama на 127.0.0.1:11434

Ноутбуки игроков → браузер → http://<IP-хоста>:2567
```

**Почему так:** на хакатоне нет интернета и времени на настройку. Игрокам ничего не нужно ставить. Сервер слушает `0.0.0.0`, чтобы его видели другие машины в сети.

**Режим разработки (`npm run dev`):** сервер на `:2567` (`tsx watch`) + Vite на `:5173` (`host: true`, виден в LAN). Клиент в dev ходит на `http://<тот же hostname>:2567`, в prod — на свой origin (`client/src/net/connection.ts`). Поэтому сервер отвечает на кросс-доменные запросы (CORS) — в dev клиент и сервер на разных портах.

  rooms/CrewRoom.ts   жизненный цикл комнаты

  ui/hud.ts            HUD: код, статус сети, экипаж, чат, приглашение

**Почему схема состояния в `shared`:** клиент передаёт класс `CrewState` в `client.create/joinById`, и `room.state` на клиенте типизирован теми же классами, что и на сервере. Без этого обработчики изменений состояния на клиенте не типизировались. `@colyseus/schema` установлен в одном экземпляре — это важно, иначе декодер не узнает классы.

## 5. Комната (`CrewRoom`)

Одна комната = один экипаж = одна игровая сессия из дизайн-дока.

### 5.1 Состояние

```ts
CrewState  { crewName: string; levelId: string; epoch: uint8; players: Map<sessionId, PlayerState> }
PlayerState{ name, color, x, y, z, vx, vy, anim, facing: int8, connected: boolean }
```

В состоянии только то, что нужно **всем** для отрисовки. `playerId` из БД хранится в `client.userData` на сервере и клиентам не уходит.

### 5.2 Жизненный цикл

| Этап | Что происходит |
|---|---|
| `onCreate` | Генерирует код комнаты и делает его `roomId`. Ставит частоту рассылки изменений состояния (patch rate) 50 мс, публикует `metadata {crewName, hostName, epoch}`, создаёт строку в `sessions`, подписывает обработчики `move` и `chat.say`, заводит таймер сохранения раз в 5 с. |
| `onAuth` | Проверяет имя (непустое, ≤ 20 символов). Отклоняет, если такое имя уже есть среди **подключённых** игроков комнаты. |
| `onJoin` | `players.findOrCreate(name)` в БД. Если у игрока есть сохранённая позиция **в этой сессии**, появляется там, иначе на точке спауна. Добавляет `PlayerState`, пишет `player.join` в журнал, отправляет событие в шину и системное сообщение в чат. |
| `onDrop` | Неожиданный обрыв: `connected=false` (у других персонаж становится полупрозрачным), `allowReconnection(client, 20 с)`. SDK на клиенте переподключается сам. |
| `onReconnect` | `connected=true`. |
| `onLeave` | Сразу сохраняет позицию, пишет `player.leave` в журнал, отправляет событие в шину, удаляет игрока из состояния. |
| `onDispose` | Финальное сохранение позиций, `sessions.finished_at`. |

### 5.3 Код комнаты

- 4 символа из алфавита `ABCDEFGHJKLMNPQRSTUVWXYZ23456789`: без `I O 0 1`, чтобы не путать при диктовке. 32⁴ ≈ 1 млн вариантов.
- Уникален и среди живых комнат (`matchMaker.getRoomById`), и среди **всех сессий в БД**. **Почему:** позиции в `player_state` привязаны к паре (игрок, сессия). Если код повторится, новая сессия получит чужие позиции.
- **Почему не стандартный `roomId`:** 9 случайных символов неудобно диктовать соседу по столу.

### 5.4 Сообщения

| Направление | Тип | Данные | Обработка |
|---|---|---|---|
| C→S | `move` | `{x,y,z,vx,vy,anim,facing}` | `sanitizeMove` → запись в `PlayerState`, игрок помечается для сохранения |
| C→S | `chat.say` | `{text}` | обрезка до 300 символов → рассылка `chat`, журнал, шина |
| S→C | `chat` | `{from,name,text,ts}` | строка в чате |
| S→C | `system` | `{text}` | системная строка («X на борту») |

Остальные типы из дизайн-дока (`grab`, `role.take`, `puzzle.action`, `agent.ask`, …) зарезервированы комментариями в `protocol.ts`.

## 6. Синхронизация движения

**Модель — клиент считает своё движение сам (клиент-авторитетная), как в разделе 6 дизайн-дока.** Каждый клиент считает физику своего персонажа, сервер принимает позицию с проверкой и рассылает остальным.

**Почему не серверная физика:** для кооперативного платформера в LAN важнее отзывчивость управления, чем защита от читов. Серверная физика с предсказанием на клиенте и сверкой с сервером заметно сложнее, а за 2 дня хакатона не окупится. Всё, где читы реально важны (головоломки, предметы, роли), будет решаться только на сервере.

### 6.1 Клиент (`LocalController`, `Game`)

- Управление: A/D или ←/→ — бег, W/S — глубина (2.5D-дорожка, z ∈ [-1.5, 1.5]), пробел — прыжок.
- Физика: `runSpeed=6`, `depthSpeed=3`, `jumpSpeed=9`, `gravity=25`, скорость падения ≤ 20. Шаг кадра ≤ 50 мс.
- Коллизии: AABB, **платформы проходимы снизу** — приземление только сверху (проверка «в прошлом кадре был выше верхней грани»). Этого хватает для хаба, Rapier не нужен.
- Падение ниже `minY` — возврат на точку спауна.
- Отправка: 20 Гц и **только если что-то изменилось** (сравнение строки с позицией, анимацией и направлением). Стоящий игрок не шлёт ничего.
- Поправка от сервера: если позиция в состоянии отличается от локальной больше чем на 3 единицы, клиент принимает серверную. Мелкие расхождения из-за задержки игнорируются.
- Ввод отключается, пока фокус в чате.

### 6.2 Сервер (`movement.ts`)

1. Отбрасывает пакет, если поля не числа или `NaN`/`Infinity`.
2. `dt` = время с прошлого пакета, **зажато в [16, 200] мс**.
3. Допустимое смещение за пакет: `скорость × 1.6 × dt` (по x — `runSpeed`, по z — `depthSpeed`, по y — max(`jumpSpeed`, `gravity·dt`) плюс 0.5). Позиция зажимается в этот коридор и в границы уровня.
4. `y < minY` → возврат на точку спауна (клиент делает то же самое, поэтому этот телепорт легален).
5. `anim` проверяется по белому списку, `facing` ∈ {1, −1}, скорости ограничены.

**Почему `dt` ограничен сверху:** без этого игрок, который не слал пакеты N секунд, получал право сместиться на `6 × 1.6 × N` — фактически телепорт. Это нашёл smoke-тест: прыжок на +13 был срезан только до +2.4. После исправления — максимум +1.92 за пакет.

**Почему множитель 1.6:** запас на неравномерные интервалы между пакетами и накопление при задержке, чтобы честный игрок не получал поправок от сервера.

### 6.3 Рассылка и отображение у других

- Сервер рассылает изменения состояния раз в 50 мс (20 Гц). Colyseus шлёт только изменившиеся поля.
- `RemotePlayer`: экспоненциальное сглаживание к целевой позиции, `k = 1 − e^(−15·dt)`. Если разница > 4 единиц (респаун, переподключение), персонаж сразу ставится в новую точку.
- Анимация процедурная (сжатие и растяжение при беге и прыжке), без скелета.

## 7. Хранение (SQLite)

### 7.1 Схема

Миграции — массив SQL в `db/db.ts`, версия хранится в `PRAGMA user_version`. Режим `journal_mode=WAL`.

| Таблица | Назначение | Используется сейчас |
|---|---|---|
| `players` | id (UUID), уникальное имя, `password_hash` (пусто), `created_at`, `last_seen_at` | да |
| `sessions` | код комнаты, название экипажа, хост, эпоха, детали, начало и конец | да |
| `player_state` | позиция и эпоха игрока в сессии, PK (player_id, session_id) | да |
| `events_log` | `player.join` / `player.leave` / `chat` с данными в JSON | да |
| `agent_memory` | память агентов об игроках (раздел 8 дизайн-дока) | нет, задел |
| `dialog_log` | реплики агентов | нет, задел |

### 7.2 Политика записи

- **Не на каждый `move`.** При 6 игроках × 20 Гц это 120 записей в секунду без пользы. Вместо этого комната копит игроков, которые двигались с прошлого сохранения, и раз в 5 с пишет их **одной транзакцией** (`playerState.saveMany`).
- Дополнительно — сразу в `onLeave` и в `onDispose`.
- Максимум теряется 5 с перемещений при падении процесса — для игры приемлемо.
- **Восстановление:** перезашёл в ту же комнату под тем же именем — появляешься там, где был. Проверено smoke-тестом.

## 8. HTTP API

Полный контракт DTO — в `shared/src/api.ts`. Авторизация — `Authorization: Bearer <token>`; токен выдаёт `POST /auth/login` (имя → JWT HS256, TTL `7d`, секрет — `JWT_SECRET` или случайный на запуск).

| Метод | Путь | Тело / доступ | Ответ |
|---|---|---|---|
| POST | `/auth/login` | `{name}` | `201 {token, player:{id, name}}` |
| POST | `/auth/logout` | Bearer | `{ok: true}` — jti в in-memory blacklist |
| GET | `/auth/me` | Bearer | `{player:{id, name}}` |
| POST | `/room` | Bearer, `{crewName?, isPublic?}` | `201 ManagedRoomInfo` — создаёт CrewRoom через matchMaker, мастер = автор |
| GET | `/room/:id` | Bearer, только мастер | `ManagedRoomInfo` |
| DELETE | `/room/:id` | Bearer, только мастер | `204` — грейсфул-удаление (позиции сохраняются, WS-каналы закрываются) |
| POST | `/room/:id/disconnect` | Bearer | `{closed: n}` — закрыть hello-каналы игрока в комнате |
| POST | `/matchmake/:method/:roomName` | опционально Bearer | `ISeatReservation` — wire-контракт `@colyseus/sdk` (`create`, `join`, `joinOrCreate`, `joinById`, `reconnect`) |
| GET | `/api/health` | — | `{ok, ts}` |
| GET | `/api/host` | — | `{addresses: string[]}` — IPv4 в LAN, сначала Wi-Fi/Ethernet |
| GET | `/api/rooms` | — | `RoomListing[]` + `isPublic` (опрос лобби раз в 3 с) |
| GET | `/api/managed-rooms` | Bearer | `ManagedRoomInfo[]` — комнаты под управлением RoomManager |
| GET | `/api/sessions`, `/api/sessions/:code` | — | сессии из БД (отладка/жюри) |
| GET | всё остальное (GET + Accept html) | — | `client/dist/index.html`, если клиент собран |

**WebSocket:** `ws://…/<processId>/<roomId>?sessionId=…` — Colyseus state; `ws://…/room/{id}/connect?token=<jwt>` — hello-канал, сервер раз в секунду шлёт `{type:'hello', text:'Hello world!', ts}`.

**Почему список комнат через REST, а не встроенный `LobbyRoom`:** проще, а опрос раз в 3 с на экране лобби в LAN ничего не стоит.

**Роли:** мастер — авторизованный создатель комнаты (`hostPlayerId` в RoomManager), удалять комнату и смотреть её карточку может только он. Гости подключаются к Colyseus-комнате через matchmake или hello-канал.

## 9. Клиент: UI

### 9.1 Лобби
- Имя запоминается в `localStorage` (обращения обёрнуты в try/catch: в приватном режиме хранилище может быть недоступно).
- «Создать комнату» с необязательным названием экипажа; «Войти по коду» (4 символа, регистр не важен); кнопки «Войти» в списке открытых комнат (неактивны, если комната заполнена).
- `/?room=CODE` в адресе — код подставляется автоматически. После входа адрес меняется на `?room=<код>`.
- Ошибки сервера переводятся в понятный текст («Комната не найдена», «Комната заполнена», «Нет связи с сервером»).

### 9.2 HUD
- Код комнаты, название экипажа, статус сети (`online` / `переподключение…`), «Выйти».
- Список экипажа с цветом игрока; отключённые полупрозрачные.
- Чат: Enter — фокус и отправка, Esc — выход из поля.

### 9.3 «Скопировать приглашение»
- **Проблема:** хост обычно открывает игру как `localhost`, и ссылка из его адресной строки у других не откроется.
- **Решение:** если hostname — `localhost`/`127.0.0.1`/`::1`, клиент берёт первый адрес из `/api/host` и подставляет его. **Порт оставляется текущий**, поэтому ссылка верна и в dev (`:5173`), и в prod (`:2567`). Если игра уже открыта по IP — ссылка строится из него.
- **Копирование:** `navigator.clipboard` работает только в защищённом контексте (https или localhost). У игроков, зашедших по `http://IP`, его нет, поэтому есть запасной путь через скрытый `textarea` и `execCommand('copy')`. Если не сработало и это, ссылка остаётся на экране 12 с с текстом «Скопируй вручную».

### 9.4 Сцена
- Перспективная камера (FOV 40, z=16) плавно следует за игроком — это и даёт 2.5D.
- Тёплый свет (полусферический + направленный с тенями), туман, слои фона на z = −4 и −9, иллюминаторы, хроно-двигатель-заглушка в центре хаба.
- Всё на примитивах three.js, без внешних ассетов и CDN — для работы офлайн.

## 10. Заготовка под ИИ

- `core/eventBus.ts` — синхронная шина. Комната публикует `session.created`, `player.join`, `player.leave`, `chat`, `session.disposed`. Ошибка в одном обработчике не роняет комнату.
- `AgentService` подписан на шину. При `DEBUG_EVENTS=1` логирует события. Дальше здесь появятся бортовой ИИ и рассказчики.
- `OllamaClient.chat()` — `POST /api/chat` с таймаутом 3 с, при ошибке возвращает `null`, и вызывающий код берёт заготовленную реплику. Включается через `OLLAMA_ENABLED=1`.

**Почему шина:** комната не должна знать про ИИ. Дизайн-док требует, чтобы игра не ждала LLM и чтобы деталь выдавала только игровая логика. Шина развязывает эти части.

## 11. Проверка

| Что | Как | Результат |
|---|---|---|
| Типы | `npm run typecheck` | чисто |
| Мультиплеер без браузера | `npm run smoke -w server` (сервер запущен): создание → комната в списке → вход второго игрока → отказ дубликату имени → 20 пакетов движения доходят до второго игрока → телепорт срезан → позиция в SQLite → после выхода у второго игрока остаётся один → перезаход на сохранённую позицию | проходит в dev и в prod |
| Auth и роли (curl) | login → me → 401 без/с кривым токеном → logout → me 401; POST /room без токена 401; DELETE гостем 403, мастером 204, повторно 404 | проходит |
| Hello-WS | проба `ws`-клиентом: 4 события с интервалами ~1 с → POST disconnect → сокет закрыт (1000); без токена — HTTP 401, чужая комната — 404 | проходит |
| UDP-бродкаст | `UDP_BROADCAST_ADDR=127.0.0.1` + `npm run udp-listen -w server`: пакеты `{roomId, crewName, host, port}` каждые 1.5 с, приватные не бродкастятся. Широковещательный адрес по умолчанию `255.255.255.255` (на реальной LAN) | проходит |

| Статика (prod) | `npm run build && npm start`: `/` и неизвестные GET с `Accept: text/html` → index.html, `/api/*` и `/room/*` мимо статикой не накрываются | проходит |
| Браузер | Две изолированные сессии headless Chrome (puppeteer-core, скрипт вне репозитория): лобби → создание → второй видит комнату в списке → вход по коду → бег и прыжок → чат → скриншоты обоих экранов; затем приглашение: копирование на хосте → второй открывает ссылку по LAN-IP → код подставлен → вход → копирование без clipboard API | проходит, ошибок в консоли нет |

**Баги, найденные при проверке и исправленные:**
1. Поля «код» и «название экипажа» не принимали ввод: `onkeydown = e => e.key === 'Enter' && …` возвращал `false`, а это отменяет нажатие клавиши.
2. Лобби не скрывалось: `display:flex` перебивал атрибут `hidden`. Добавлено правило `[hidden] { display: none !important }`.
3. Сервер разрешал «телепорт» после паузы в пакетах — ограничен `dt` (см. 6.2).
4. Глаза персонажа были внутри куба — вынесены на лицевую грань.

## 12. Известные ограничения и долг

| Ограничение | Последствие | Как закрыть |
|---|---|---|
| Игрок определяется только по имени | Кто угодно может зайти под чужим именем и получить его сохранённую позицию | Токен уже есть (`POST /auth/login`); осталось требовать его в `static onAuth(token)` комнаты и мэтчить игрока по `sub`, а не по `options.name`. Пароль при необходимости — поле `password_hash` в схеме. |
| Комнаты Colyseus принимают анонимный вход | matchmake без токена проходит (`@colyseus/auth` пропускает анонима); авторизация обязательна только в REST/hello-API | Требовать Bearer в matchmake-роуте, когда фронт перейдёт на токены |
| Сервер не проверяет коллизии с платформами | Можно проходить сквозь платформы и «лететь» вверх в пределах лимита скорости | Перенести проверку «стоит на опоре» на сервер, если станет важно |
| Проверка дубликата имени — только среди подключённых | Пока игрок ждёт переподключения (20 с), под его именем может войти второй — в состоянии будут два игрока с одним именем | Учитывать и отключённых, либо отдавать новому входу место отключённого |
| Сглаживание вместо буфера снимков | При большой задержке или потерях пакетов возможны рывки | Буфер снимков с отставанием ~100 мс |
| Комнаты живут в памяти | После перезапуска сервера комнат нет, данные в БД остаются, но продолжить старую сессию нельзя | Восстановление комнаты по коду из `sessions` |
| Сценарий `onLeave` после неудачного переподключения не проверен тестом | — | Добавить в smoke обрыв соединения |
| В prod сервер запускается через `tsx` без сборки | Медленнее старт, не критично | `tsc`/`tsup`-сборка, если понадобится |
| CORS разрешает любой источник | Приемлемо в закрытой LAN | Ограничить, если сервер станет доступен извне |
| `node:sqlite` помечен experimental | Предупреждение в логе | Стабилен в Node 22/24, API простой |
| Бандл клиента ~660 КБ (three.js целиком) | Предупреждение Vite, в LAN не важно | Разбивка на чанки при необходимости |

## 13. Как расширять

1. Новый тип сообщения → `shared/src/protocol.ts`.
2. Синхронизируемые поля → `shared/src/schema.ts`. **Приватные данные ролей (Наблюдатель/Механик) — не в общее состояние**, а через `StateView` / `@view()` или адресный `client.send`, иначе их видно в DevTools.
3. Обработчик → `CrewRoom.onCreate` или отдельная система (`server/src/puzzles/*.ts`), которой комната делегирует.
4. Значимые события → `eventBus.emit(...)`.
5. Клиент: подписки через `net.callbacks(room)` (`onAdd` / `onRemove` / `listen` / `onChange`).
6. Новый REST-эндпоинт → `server/src/http/app.ts`, DTO → `shared/src/api.ts`, регистрация экспорта — в `shared/src/index.ts`.
7. Новая таблица → новая строка в массиве `MIGRATIONS` (старые миграции не менять).
